# Shortest Subarray with Sum at Least K — Building Intuition

## The Problem

Given an integer array `nums` (which **can contain negatives**) and an integer `k`, find the length of the shortest non-empty subarray with sum >= k. Return -1 if none exists.

This is LeetCode 862, and it's a hard upgrade from LeetCode 209 (Minimum Size Subarray Sum) where all elements are positive.

---

## 0. Two Prefix Sum Conventions

There are two common ways to define the prefix sum array. The choice affects the subarray sum formula and how you compute window length.

### Convention 1: P[0] = A[0] (array of length n)

```
P[0] = A[0]
P[1] = A[0] + A[1]
...
P[i] = A[0] + A[1] + ... + A[i]
```

**Example**:

```
A    = [3,  1,  4,  1,  5]
        0   1   2   3   4

P    = [3,  4,  8,  9, 14]
        0   1   2   3   4
```

Building P step by step:
```
P[0] = A[0] = 3
P[1] = A[0] + A[1] = 3 + 1 = 4
P[2] = A[0] + A[1] + A[2] = 4 + 4 = 8
P[3] = A[0] + ... + A[3] = 8 + 1 = 9
P[4] = A[0] + ... + A[4] = 9 + 5 = 14
```

**Subarray sum** of `A[i..j]` (inclusive both ends):

```
sum(A[i..j]) = P[j] - P[i-1]    (when i > 0)
sum(A[i..j]) = P[j]              (when i == 0, no P[-1] exists)
```

Examples using `A = [3, 1, 4, 1, 5]`:
```
sum(A[1..3]) = P[3] - P[0] = 9 - 3 = 6     →  1+4+1 = 6  ✓
sum(A[2..2]) = P[2] - P[1] = 8 - 4 = 4     →  4 = 4  ✓
sum(A[0..4]) = P[4]         = 14             →  3+1+4+1+5 = 14  ✓  (edge case! can't use P[-1])
sum(A[0..2]) = P[2]         = 8              →  3+1+4 = 8  ✓  (edge case again)
```

**Window length**:

```
j - i + 1 = j - (i-1)       (when i > 0)
j + 1                        (when i == 0)
```

Here the P-array indices are `j` and `i-1`, and again the gap equals the subarray length. But the `i == 0` case requires special handling since there is no `P[-1]`.

```
A[1..3]: P-indices are 3 and 0 → length = 3 - 0 = 3  ✓
A[0..4]: no left P-index       → length = 4 + 1 = 5  ✓  (special case)
```

### Convention 2: P[0] = 0 (array of length n+1)

```
P[0] = 0
P[1] = A[0]
P[2] = A[0] + A[1]
...
P[i] = A[0] + A[1] + ... + A[i-1]
```

**Example**:

```
A    = [3,  1,  4,  1,  5]
        0   1   2   3   4

P    = [0,  3,  4,  8,  9, 14]
        0   1   2   3   4   5
       ↑
       sentinel (sum of zero elements)
```

Building P step by step:
```
P[0] = 0                          (sentinel)
P[1] = 0 + A[0] = 0 + 3 = 3
P[2] = 0 + A[0] + A[1] = 3 + 1 = 4
P[3] = 0 + A[0] + A[1] + A[2] = 4 + 4 = 8
P[4] = 0 + ... + A[3] = 8 + 1 = 9
P[5] = 0 + ... + A[4] = 9 + 5 = 14
```

**Subarray sum** of `A[i..j]` (inclusive both ends):

```
sum(A[i..j]) = P[j+1] - P[i]
```

Examples using `A = [3, 1, 4, 1, 5]`:
```
sum(A[0..2]) = P[3] - P[0] = 8 - 0 = 8     →  3+1+4 = 8  ✓
sum(A[1..3]) = P[4] - P[1] = 9 - 3 = 6     →  1+4+1 = 6  ✓
sum(A[0..4]) = P[5] - P[0] = 14 - 0 = 14   →  3+1+4+1+5 = 14  ✓  (full array, no edge case!)
sum(A[2..2]) = P[3] - P[2] = 8 - 4 = 4     →  4 = 4  ✓  (single element)
```

**Window length**:

```
j - i + 1 = (j+1) - i
```

Notice that `(j+1)` and `i` are exactly the two indices into the P array. So the subarray length equals the gap between the P-array indices directly. No off-by-one adjustment needed.

```
A[1..3]: P-indices are 4 and 1 → length = 4 - 1 = 3  ✓  (elements: 1, 4, 1)
A[0..4]: P-indices are 5 and 0 → length = 5 - 0 = 5  ✓  (full array)
```

### Side-by-Side Summary

| | Convention 1: P[0] = A[0] | Convention 2: P[0] = 0 |
|---|---|---|
| P length | n | n + 1 |
| P definition | `P[i] = A[0] + ... + A[i]` | `P[i] = A[0] + ... + A[i-1]` |
| sum(A[i..j]) | `P[j] - P[i-1]` (i>0), `P[j]` (i=0) | `P[j+1] - P[i]` |
| Window length | `j - (i-1)` (gap of P indices) | `(j+1) - i` (gap of P indices) |
| Edge case at i=0 | Must special-case — no `P[-1]` | None — `P[0] = 0` handles it |

Convention 1 is the more natural definition — `P[i]` is the sum of the first `i+1` elements, and it maps 1-to-1 with the original array indices. The tradeoff is the `i=0` edge case when computing subarray sums.

Convention 2 introduces a sentinel `P[0] = 0`, which eliminates that edge case at the cost of the P array being one element longer and its indices being shifted by 1 from the original array.

All solutions below use **Convention 1**. Section 6 shows how Convention 2 simplifies the code.

## 1. Why the Sliding Window from LC 209 Breaks

In LC 209, the classic two-pointer/sliding window works beautifully:

```cpp
int left = 0, sum = 0, ans = INT_MAX;
for (int right = 0; right < n; right++) {
    sum += nums[right];
    while (sum >= k) {
        ans = min(ans, right - left + 1);
        sum -= nums[left];
        left++;
    }
}
```

This relies on **two guarantees** that positive-only arrays give us:

1. **Expanding (moving right) always increases the sum.** So if our sum is too small, moving right will eventually fix it.
2. **Shrinking (moving left) always decreases the sum.** So once the sum drops below k, we know we must stop shrinking and go back to expanding.

These two properties make the sum behave **monotonically** with respect to window size. The window acts like a dial: turn it wider, sum goes up; turn it narrower, sum goes down.

**Negative numbers destroy both guarantees.**

- Expanding can **decrease** the sum (we added a negative).
- Shrinking can **increase** the sum (we removed a negative from the left).

### Concrete Example

```
nums = [84, -37, 32, 40, 95],  k = 167
```

Walk through the sliding window:

```
right=0: window=[84],              sum=84   (< 167, expand)
right=1: window=[84,-37],          sum=47   (< 167, expand)
right=2: window=[84,-37,32],       sum=79   (< 167, expand)
right=3: window=[84,-37,32,40],    sum=119  (< 167, expand)
right=4: window=[84,-37,32,40,95], sum=214  (>= 167! record length 5)
  shrink: window=[-37,32,40,95],   sum=130  (< 167, stop shrinking)
```

Sliding window says: **answer = 5**.

But `[32, 40, 95]` sums to 167, and has length **3**. That's the real answer.

**What went wrong?** When the window was `[84, -37, 32, 40, 95]` and we removed `84` from the left, the sum dropped to 130 < 167, so we stopped. We never considered that removing *both* `84` and `-37` would bring the sum back up to 167. The sliding window is a greedy algorithm — it sees removing `84` hurt the sum and gives up. It doesn't anticipate that removing the `-37` would *help*.

**The core issue**: with negatives, the "should I shrink or expand?" decision is no longer locally deterministic. Shrinking might hurt now but help later (removing a negative after removing a positive). The greedy invariant is broken.

## 2. How Prefix Sums Reframe the Problem

Since the sliding window's local reasoning fails, we need a global view. Prefix sums give us that.

Using Convention 1:

```
P[0] = nums[0]
P[1] = nums[0] + nums[1]
...
P[i] = nums[0] + nums[1] + ... + nums[i]
```

The sum of any subarray `nums[i..j]` is:

```
sum(nums[i..j]) = P[j] - P[i-1]    (when i > 0)
sum(nums[i..j]) = P[j]              (when i == 0)
```

Now our problem becomes a **pair-search on P**:

For each index `j`, we look for an index `idx` in P such that `P[j] - P[idx] >= k`. Here `idx` plays the role of `i-1`, so the actual subarray is `nums[idx+1..j]` with length `j - idx`.

We also must check `P[j] >= k` separately — that's the subarray `nums[0..j]` with length `j + 1`.

For our example:

```
nums =  [84, -37,  32,  40,  95]
P    = [84,  47,  79, 119, 214]
        0    1    2    3    4
```

Pair-search candidates and edge case check:

| Type | idx | j | Calculation | Sum >= k? | Subarray | Length | Result |
|---|---|---|---|---|---|---|---|
| Pair-search | 0 | 4 | P[4]-P[0] = 214-84 = 130 | 130 < 167 ✗ | — | — | skip |
| Pair-search | 1 | 4 | P[4]-P[1] = 214-47 = 167 | 167 >= 167 ✓ | nums[2..4] = [32,40,95] | 4-1 = 3 | **answer** |
| Edge case | — | 4 | P[4] = 214 | 214 >= 167 ✓ | nums[0..4] = full array | 4+1 = 5 | valid but longer |

This algebraic restatement is clean, but a brute-force check of all pairs is O(n²). We need structure to search efficiently.

## 3. The "Dip" Insight — Why Dominated Indices Can Be Discarded

Let's look at our prefix sum visually:

```
P[idx]
  |
84 | *  (idx=0)
   |
79 |          *  (idx=2)
   |
47 |     *  (idx=1)
   |
   +--+--+--+--+--→ idx
     0  1  2  3  4
```

Notice the **dip** from P[0]=84 down to P[1]=47. This dip is caused by `nums[1] = -37`.

Now here's the critical observation. Remember each deque index `idx` represents a potential left boundary — the subarray would be `nums[idx+1..j]`. For any future index `j`, would we ever prefer `idx=0` over `idx=1`?

- **Sum comparison**: `P[j] - P[1]` >= `P[j] - P[0]` because P[1] < P[0]. So idx=1 always gives an **equal or larger** subarray sum.
- **Length comparison**: `j - 1` < `j - 0`. So idx=1 always gives a **shorter** subarray.

Index 1 **dominates** index 0 on both axes. Index 0 is useless as a pair-search candidate.

**General rule**: If `idx1 < idx2` and `P[idx1] >= P[idx2]`, then `idx1` is permanently dominated by `idx2`. Any valid subarray using `idx1` has a valid, shorter counterpart using `idx2`.

This means among our pair-search candidates, we only care about indices where the prefix sum is **strictly increasing** — a monotonically increasing subsequence of prefix sums. Any "dip" in the prefix sum curve renders earlier, higher values obsolete.

Applying this to our example:

```
P = [84, 47, 79, 119, 214]

idx=0: P=84  → keep (first element)
idx=1: P=47  → 47 < 84, so idx=0 is dominated. Discard idx=0, keep idx=1.
idx=2: P=79  → 79 > 47, keep.
idx=3: P=119 → 119 > 79, keep.

Surviving candidates: [1, 2, 3] with P values [47, 79, 119] — strictly increasing.
```

Index 0 was eliminated by the dip. This is the structural insight that powers both the heap and deque solutions.

> **Note**: The dip insight applies to the pair-search part of the problem. The separate `P[j] >= k` check (subarrays starting at index 0) is handled independently and isn't affected by this pruning.

## 4. Min-Heap Solution — O(n log n)

### Idea

For each `j`, we want to find some `idx < j` where `P[idx]` is small enough that `P[j] - P[idx] >= k`, and `idx` is as **large** (close to `j`) as possible to minimize the window length `j - idx`.

A min-heap keyed on `P[idx]` always gives us the **smallest** available prefix sum at the top. If even the smallest P[idx] doesn't satisfy `P[j] - P[idx] >= k`, no other will either.

### Key Insight: Why We Can Pop

Once `P[j] - P[idx] >= k` for some pair, can any future `j' > j` do better with this same `idx`? No — `j' - idx > j - idx`, so the subarray would be longer. We've already recorded the best answer this `idx` can produce, so we pop it.

### Algorithm

```cpp
class Solution {
public:
    int shortestSubarray(vector<int>& nums, int k) {
        int n = nums.size();
        vector<long long> P(n);
        P[0] = nums[0];
        for (int i = 1; i < n; i++) {
            P[i] = P[i - 1] + nums[i];
        }

        int ans = INT_MAX;
        // min-heap of {prefix_sum, index}
        priority_queue<pair<long long, int>,
                       vector<pair<long long, int>>,
                       greater<pair<long long, int>>> pq;

        for (int j = 0; j < n; j++) {
            // Edge case: subarray nums[0..j] — no P index to subtract
            if (P[j] >= k) {
                ans = min(ans, j + 1);
            }

            // Try to form valid subarrays with the smallest prefix sums
            while (!pq.empty() && P[j] - pq.top().first >= k) {
                auto [val, idx] = pq.top();
                pq.pop();
                ans = min(ans, j - idx);  // subarray nums[idx+1..j], length = j - idx
            }

            pq.push({P[j], j});
        }

        return ans == INT_MAX ? -1 : ans;
    }
};
```

### Walkthrough

```
nums = [84, -37, 32, 40, 95],  k = 167
P    = [84,  47, 79, 119, 214]

j=0: P[0]=84
     P[0]=84 >= 167? No
     heap empty → push (84,0)
     heap: [(84,0)]

j=1: P[1]=47
     P[1]=47 >= 167? No
     top=(84,0), 47-84 = -37 < 167 → no pop
     push (47,1)
     heap: [(47,1), (84,0)]

j=2: P[2]=79
     P[2]=79 >= 167? No
     top=(47,1), 79-47 = 32 < 167 → no pop
     push (79,2)
     heap: [(47,1), (84,0), (79,2)]

j=3: P[3]=119
     P[3]=119 >= 167? No
     top=(47,1), 119-47 = 72 < 167 → no pop
     push (119,3)

j=4: P[4]=214
     P[4]=214 >= 167? Yes! → ans = min(∞, 4+1) = 5
     top=(47,1), 214-47 = 167 >= 167 → pop! ans = min(5, 4-1) = 3
        (subarray nums[2..4] = [32,40,95], length 3)
     top=(79,2), 214-79 = 135 < 167 → stop
     push (214,4)

Answer: 3 ✓
```

### Complexity

- **Time**: O(n log n) — each index is pushed and popped from the heap at most once, each operation is O(log n).
- **Space**: O(n) for the prefix array and heap.

### Why Not O(n)?

The heap gives us the smallest prefix sum, but not necessarily the one closest to `j`. We're always popping the globally smallest, which is correct but requires log-time operations. Can we do better?

## 5. Monotonic Deque Solution — O(n)

### Building on the Dip Insight

We established two things:

1. **Dominated indices are useless** (the dip insight): if `P[idx2] <= P[idx1]` and `idx2 > idx1`, discard `idx1`.
2. **Consumed indices are useless**: once index `idx` forms a valid pair with `j`, any future `j'` would give a longer answer with the same `idx`.

A **monotonic deque** (double-ended queue) maintains exactly the set of useful pair-search candidates, in increasing order of both index and prefix sum.

### The Two Operations

For each `j`, we do two things (plus the edge case check):

**Edge case — subarrays starting at index 0:**

```cpp
if (P[j] >= k) {
    ans = min(ans, j + 1);  // subarray nums[0..j]
}
```

**Front of deque — try to answer:**

```cpp
while (!dq.empty() && P[j] - P[dq.front()] >= k) {
    ans = min(ans, j - dq.front());  // subarray nums[dq.front()+1..j]
    dq.pop_front();   // consumed — won't give a shorter answer later
}
```

Why pop from front? The front has the smallest index (farthest from `j`). If it satisfies the sum condition, record it. But any future `j' > j` would make the subarray longer, so this index is done. Pop it and check the next one — which has a larger index (closer to `j`), potentially giving an even shorter answer.

**Back of deque — maintain monotonicity:**

```cpp
while (!dq.empty() && P[j] <= P[dq.back()]) {
    dq.pop_back();   // dominated — j is a better candidate
}
```

This enforces the dip insight. If the current prefix sum is <= the back of the deque, the back is dominated and can be removed.

**Then push `j` onto the back.**

### Full Algorithm

```cpp
class Solution {
public:
    int shortestSubarray(vector<int>& nums, int k) {
        int n = nums.size();
        vector<long long> P(n);
        P[0] = nums[0];
        for (int i = 1; i < n; i++) {
            P[i] = P[i - 1] + nums[i];
        }

        int ans = INT_MAX;
        deque<int> dq;  // stores indices; P values are strictly increasing

        for (int j = 0; j < n; j++) {
            // Edge case: subarray nums[0..j] — no P index to subtract
            if (P[j] >= k) {
                ans = min(ans, j + 1);
            }

            // 1. Try to form valid subarrays from front
            while (!dq.empty() && P[j] - P[dq.front()] >= k) {
                ans = min(ans, j - dq.front());  // subarray nums[dq.front()+1..j]
                dq.pop_front();
            }

            // 2. Maintain increasing monotonicity from back
            while (!dq.empty() && P[j] <= P[dq.back()]) {
                dq.pop_back();
            }

            // 3. Add current index
            dq.push_back(j);
        }

        return ans == INT_MAX ? -1 : ans;
    }
};
```

### Why This Is O(n)

Every index enters the deque exactly once (pushed onto the back) and leaves at most once (popped from front or back). So across all iterations of `j`, the total number of deque operations is at most 2n. Each operation is O(1). The `P[j] >= k` check is O(1) per iteration. Total: **O(n)**.

## 6. Using Convention 2 — P[0] = 0 (Sentinel)

All solutions above use Convention 1 (`P[0] = A[0]`, length `n`). Let's redo them with Convention 2 (`P[0] = 0`, length `n+1`) to see how the sentinel eliminates the edge case.

### How the Pair-Search Changes

With Convention 2:

```
P[0] = 0,  P[1] = A[0],  P[2] = A[0]+A[1],  ...,  P[i] = A[0]+...+A[i-1]
```

The subarray sum `A[i..j]` is uniformly:

```
P[j+1] - P[i]       (works for ALL i, including i=0)
```

The pair-search becomes: for each `j` (index into P, ranging 0 to n), find an index `i` in P such that `P[j] - P[i] >= k`. The window length is simply `j - i`. No special cases.

Why does `i=0` work? Because `P[0] = 0`, so `P[j] - P[0] = P[j]`, which is the sum of `A[0..j-1]` — exactly the edge case Convention 1 had to handle separately.

### What the Deque/Heap Store

| | Convention 1: P[0] = A[0] | Convention 2: P[0] = 0 |
|---|---|---|
| P range | `0..n-1` | `0..n` |
| Deque stores | `idx` (subarray starts at `idx+1`) | `i` (left endpoint directly) |
| Sum condition | `P[j] - P[idx] >= k` | `P[j] - P[i] >= k` |
| Window length | `j - idx` | `j - i` |
| Edge case | Must check `P[j] >= k` separately | None — `P[0] = 0` handles it |

The formulas look identical, but Convention 2 needs no `if` check — the sentinel `P[0] = 0` enters the deque/heap as a regular candidate and naturally handles subarrays starting at index 0.

### Min-Heap with Convention 2

```cpp
class Solution {
public:
    int shortestSubarray(vector<int>& nums, int k) {
        int n = nums.size();
        vector<long long> P(n + 1, 0);
        for (int i = 0; i < n; i++) {
            P[i + 1] = P[i] + nums[i];
        }

        int ans = INT_MAX;
        // min-heap of {prefix_sum, index}
        priority_queue<pair<long long, int>,
                       vector<pair<long long, int>>,
                       greater<pair<long long, int>>> pq;

        for (int j = 0; j <= n; j++) {
            // No edge case needed — P[0]=0 is in the heap as a regular candidate
            while (!pq.empty() && P[j] - pq.top().first >= k) {
                auto [val, i] = pq.top();
                pq.pop();
                ans = min(ans, j - i);
            }

            pq.push({P[j], j});
        }

        return ans == INT_MAX ? -1 : ans;
    }
};
```

### Monotonic Deque with Convention 2

```cpp
class Solution {
public:
    int shortestSubarray(vector<int>& nums, int k) {
        int n = nums.size();
        vector<long long> P(n + 1, 0);
        for (int i = 0; i < n; i++) {
            P[i + 1] = P[i] + nums[i];
        }

        int ans = INT_MAX;
        deque<int> dq;  // stores indices; P values are strictly increasing

        for (int j = 0; j <= n; j++) {
            // No edge case needed — P[0]=0 handles subarrays starting at index 0

            // 1. Try to form valid subarrays from front
            while (!dq.empty() && P[j] - P[dq.front()] >= k) {
                ans = min(ans, j - dq.front());
                dq.pop_front();
            }

            // 2. Maintain increasing monotonicity from back
            while (!dq.empty() && P[j] <= P[dq.back()]) {
                dq.pop_back();
            }

            // 3. Add current index
            dq.push_back(j);
        }

        return ans == INT_MAX ? -1 : ans;
    }
};
```

```
     front: P[3]-P[0] = 79 < 167 → skip
     back:  79 > 47 → keep
     push 3.   dq = [0, 2, 3]
     (P values: [0, 47, 79])

     front: P[4]-P[0] = 119 < 167 → skip

```

Notice how `P[0] = 0` at index 0 naturally produced the length-5 answer (`5 - 0 = 5`) without any special-case `if` statement. The sentinel got pushed, survived monotonicity checks, and was consumed from the front just like any other candidate. Clean and uniform.

### Convention 2 Is Cleaner for Implementation

Convention 2 folds the edge case into the data structure. By setting `P[0] = 0` and iterating `j` from 0 to n, the sentinel value `P[0] = 0` enters the deque/heap as just another candidate. When `P[j] - P[0] >= k`, that's the subarray `A[0..j-1]` — no special case, no `if` statement, no `j+1` length calculation. The pair-search formula handles everything uniformly.

Convention 1 forces you to remember the edge case, use a different length formula for it (`j+1` vs `j-idx`), and adds a branch to every iteration. The logic is correct but noisier. In an interview or contest, that extra branch is where bugs hide.

## Summary — The Progression of Ideas

| Step | Insight | Approach | Time |
|------|---------|----------|------|
| 1 | Sliding window assumes monotonic sums | Fails with negatives | — |
| 2 | Prefix sums turn it into a pair-search problem | Brute force all pairs | O(n²) |
| 3 | Dips in prefix sum create dominated indices | Only keep useful candidates | — |
| 4 | Min-heap surfaces the smallest P[idx] first | Pop consumed indices greedily | O(n log n) |
| 5 | Monotonic deque maintains candidates in order of both index and value | Pop from front (consumed) and back (dominated) | **O(n)** |

The deque solution is elegant because it handles both "consumed" and "dominated" indices through its two ends — front pops exploit the fact that the smallest-index valid candidate is the first to expire, and back pops enforce the dip insight that keeps the deque's prefix sums strictly increasing.
